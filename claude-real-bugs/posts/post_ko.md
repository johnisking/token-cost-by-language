# 실제 버그 25개로 비교한 Claude 하이쿠 vs 오퍼스: 깔끔한 수정 52 대 54, 비용은 95% 적게

지난주에는 Claude 하이쿠 5.5가 오퍼스보다 뒤처지는 지점을 찾았습니다. 답은 marked 파서의 어려운 버그 하나였습니다. 신고문에 없던 경계 사례를 소넷과 오퍼스는 자주 챙겼고 하이쿠는 거의 놓쳤습니다. 하지만 버그 하나로는 근거가 약해서, 이번에는 세 모델에게 실제 버그 25개를 맡겼습니다.

**요약:** 하이쿠는 오퍼스만큼 버그를 깔끔하게 고쳤고(75회 중 52회 대 54회), 비용은 약 95% 적었습니다. 어려운 버그에서는 오퍼스가 앞섰는데, 주로 다른 테스트를 덜 깨뜨렸기 때문입니다. 그리고 신고문이 빠뜨린 경우는 세 모델 모두 똑같이 놓쳤습니다.

## 측정 방법

- **버그 25개:** 2026년 8~10월에 실제로 고쳐진 오픈소스 프로젝트 13개의 버그입니다. js-yaml, jsdiff, qs, PapaParse, markdown-it, marked, zod, humanize, tomlkit, more-itertools, cachetools, Python-Markdown, pyparsing.
- **시작점:** 수정 직전 커밋입니다. 의존성은 설치해 두고 git 기록은 지워서, 정답 커밋을 찾아볼 수 없게 했습니다.
- **프롬프트:** 신고문에서 증상만 남겼습니다. 무엇이 잘못되는지, 재현 방법, 기대 결과만 있고 원인 분석과 수정 제안은 지웠습니다.
- **Claude Code 2.1.295**를 무인 모드, effort medium으로 돌렸습니다. 파일 읽기와 수정, 프로젝트 테스트 실행은 허용했고 패키지 설치와 네트워크는 막았습니다.
- **버그와 모델마다 3회**, 모두 225회입니다.
- **채점:** 실행 결과에서 라이브러리 소스 변경만 가져오고(모델이 쓴 테스트는 버림), **관리자들이 그 수정과 함께 넣은 테스트**를 돌렸습니다. 다른 곳을 깨뜨렸는지는 프로젝트 테스트로 확인했습니다.

버그는 두 단계로 나눴습니다. **쉬운 단계**(15개)는 원인과 증상이 가까이 있는 버그이고, **어려운 단계**(10개)는 신고문에 증상만 있고 원인은 다른 곳에 있는 경우가 많은 버그입니다.

"깔끔한 수정"은 관리자의 테스트 사례를 모두 통과하고, 다른 테스트를 하나도 깨뜨리지 않은 경우입니다.

| | 하이쿠 5.5 | 소넷 5.5 | 오퍼스 5.5 |
|---|---|---|---|
| 깔끔한 수정, 쉬운 단계 | 40/45 | 35/45 | 38/45 |
| 깔끔한 수정, 어려운 단계 | 12/30 | 14/30 | 16/30 |
| **깔끔한 수정, 전체** | **52/75** | **49/75** | **54/75** |
| 다른 테스트를 깨뜨린 실행 (어려운 단계) | 10 | 7 | 5 |
| 1회 비용 (API 가격 기준) | $0.019 | $0.14 | $0.38 |
| 75회 합계 | $1.41 | $10.83 | $28.53 |

25개 중 22개 버그에서 하이쿠와 오퍼스의 깔끔한 수정 횟수는 똑같았습니다. 달랐던 3개는 다음과 같습니다.

- **marked, 링크 텍스트 안의 링크:** 오퍼스는 3번 중 2번 깔끔하게 고쳤고 하이쿠는 0번이었습니다. 하이쿠는 3번 모두 바로 그 예시의 스펙 테스트를 깨뜨렸습니다.
- **markdown-it, 닫히지 않은 링크 라벨이 코드 구간을 가리는 버그:** 오퍼스 3번 중 3번, 하이쿠 1번입니다. 하이쿠 2번은 버그는 고쳤지만 옆의 테스트 2개를 깨뜨렸습니다.
- **js-yaml, 공백만 있는 블록 스칼라:** 이번엔 하이쿠가 3번 중 3번, 오퍼스 1번, 소넷 0번이었습니다.

하나 더 있습니다. **zod**에서 숫자 키 레코드를 JSON Schema 여러 곳에서 처리해야 하는 버그는 완전히 고친 실행이 없었지만, 3회 합계로 테스트 사례 24개 중 오퍼스가 14개, 하이쿠 9개, 소넷 5개를 통과했습니다.

## 어떤 모델도 못 찾은 것

어려운 버그 3개에서는 모든 모델의 모든 실행이 신고문의 예시는 고치고, 신고문에 없던 같은 경우를 놓쳤습니다.

- **cachetools:** 신고문은 클래스를 통해 캐시 메서드를 부르는 한 가지 방법만 보여 줬습니다. 관리자들은 데코레이터의 다른 변형까지 모두 테스트했고, 이를 처리한 실행은 없었습니다.
- **js-yaml:** 신고문은 파일 맨 앞의 BOM 문제였습니다. 관리자들은 여러 문서가 이어진 스트림에서 문서마다 붙은 BOM도 테스트했고, 이를 처리한 실행은 없었습니다.
- **Python-Markdown:** 모든 실행이 신고된 HTML 주석 문제는 고쳤지만, 다른 인라인 HTML 뒤에 오는 주석에 대한 관리자 테스트를 3~5개씩 깨뜨렸습니다.

지난번에는 소넷과 오퍼스가 이런 경우를 더 잘 찾았는데, 버그 25개로 넓히자 그 패턴은 유지되지 않았습니다. 큰 모델에 돈을 더 내도 빠진 경우는 나오지 않았고, 관리자의 테스트를 읽는 쪽이 그 경우를 찾아냈을 겁니다.

## 이 차이는 진짜일까

이 정도 규모로는 가려내기 어렵다고 봅니다. 조심해서 말씀드리겠습니다.

- **하이쿠 대 오퍼스, 전체:** 깔끔한 수정에 대한 피셔 정확 검정 p = 0.86입니다. 버그 단위로 다시 뽑아 보면 하이쿠에서 오퍼스를 뺀 차이의 95% 구간은 −11%p에서 +5%p입니다. 오퍼스가 버그를 더 많이 고친다는 증거는 없지만, 10%p 정도의 차이까지 없다고 할 수는 없습니다.
- **어려운 단계만:** 구간이 −33%p에서 0%p입니다. 이런 버그에서는 오퍼스가 정말 나을 수 있지만, 버그 10개로는 말할 수 없습니다.
- **소넷**은 전체 테스트 사례 통과율이 오퍼스보다 낮았습니다(짝지은 순열 검정 p = 0.006). 분명하게 유의한 차이는 이것 하나입니다.

두 모델이 ±10%p 안에서 같다고 보이려면 모델당 수백 회, 서로 다른 버그가 필요합니다. 같은 방법으로 버그를 계속 늘려 갈 생각입니다.

## 정리

- **원인이 증상 가까이에 있는 버그는 하이쿠로 충분합니다.** 깔끔한 수정 횟수가 오퍼스와 같고 비용은 약 95% 적습니다.
- **여러 곳을 함께 고쳐야 하는 버그는 오퍼스가 더 안전합니다.** 어려운 단계에서 다른 테스트를 깨뜨린 실행이 하이쿠의 절반이었습니다(5회 대 10회).
- **신고문이 빠뜨린 경우는 어떤 모델도 찾지 못합니다.** 어려운 단계에서 모델마다 실행의 47~60%가 깔끔한 수정이 아니었습니다. 어떤 모델을 쓰든 검토 시간은 여기에 써야 합니다.
